## 5. Что зафиксировано по пунктам 3.1–3.4

### 3.1. Столкновения в `collisions.ts`: O(n²) → O(n)

> Реализовано в PR #4C; доказательство эквивалентности и измерения — раздел 9.

* Текущий двойной цикл по `world.tokens.keys()` действительно даёт n(n−1)/2 сравнений (4950 при 100 сферах,
  499 500 при 1000).
* Готов **эталон эквивалентности**: тест `swap index: linear index and the O(n²) scan agree on 1500 seeded
  configurations with the swapper exception` строит 1500 случайных раскладок, считает вердикт независимой
  линейной реализацией из плана и требует совпадения с текущим перебором.
* Важно: **исключение swapper — не мёртвый код.** 180°-поворот переставляет сферы через две клетки
  (`pivot ± dir`), и такая пара попадает в условие `new1 == old2 && new2 == old1`. Тест
  `the swapper exception covers its own two-hex exchange, while two jumpers exchanging spheres collide`
  фиксирует и это, и обратный случай: обмен двух сфер трамплинами без сваппера — столкновение.
* Предположение об уникальности стартовых гексов безопасно: инвариант B гарантирует, что после каждого
  завершённого такта на гексе не больше одной сферы (проверяется фаззингом), а двойной вход в сумматор/весы
  существует только в *предлагаемых* координатах, не в стартовых.
* Порядок проверок нельзя переставлять: текущий перебор обмена выполняется **после** проверок края, корпуса,
  разлома и **до** проверки наложений. Линейный индекс обязан сохранить этот порядок, иначе изменятся тексты
  ошибок в сценариях с несколькими нарушениями сразу (см. `simultaneous-collision-report`).

### 3.2. Стабильный `compareIntents`

Сейчас выбор действительно зависит от порядка обхода: см. `equal-intent-choice` и
`pusher-magnet-move-source`. Координаты не меняются, поэтому это P2. Тесты готовы к переключению на
`assertMatchesRule` после введения `compareIntents` (сначала tier/signature, затем `pushChainIndex`,
координата источника, тип механизма).

### 3.3. Геометрия вращения

* Математика в порядке: `R^6 = id`, `R^3∘R^3 = id`, `d(R(A),R(B)) = d(A,B)` — проверено исчерпывающе на
  сетке ±6 и на всех парах ±4 для трёх пивотов и шагов ±1/±3.
* 60° свободного вращения полимера, корпус на дуге, «чужая» сфера на дуге, корпус в точке назначения,
  сваппер-поворот полимера на 180°, атомарность при корпусе в точке назначения — всё работает.
* Выборка дуги: на момент аудита #4A для радиусов 2–5 десять точек покрывали 200-точечную эталонную выборку в протестированных координатах, а на радиусе 6 обнаружен пропуск (`-4,-3`). В PR #4D выборка заменена аналитическим пересечением дуги с гексами (см. раздел 10 и `docs/rotation-geometry-contract.md`), поэтому плотная выборка осталась в тестах только как независимый эталон.

### 3.4. Источники и индексы занятости

> Реализовано в PR #4C; правило общего выхода сохранено, измерения — раздел 9.

* Критерий синхронности зафиксирован тестом `sources: occupancy is checked after movement, so a hex freed in
  the same tick can be used immediately`: источник обязан видеть мир **после** фазы движения.
* Ожидание при занятом выходе и последующий выпуск проверены отдельным тестом; два источника на одной линии
  не перезаписывают значения друг друга.
* Индекс занятости нужно строить локально в `activateSpawners` и обновлять сразу после создания сферы
  (как в плане). Общий `TickContext` по-прежнему не нужен: других потребителей индекса нет.

## 9. PR #4C — оптимизация движения

Дата: 2026-11-17 · База: `main` @ `42a88a1` · Ветка: `arena/6ba54554-formulfabric`
(имя `perf/movement-indexes` недоступно: среда фиксирует рабочую ветку сессии) · PR:
[#6](https://github.com/resarytrew/FormulFabric/pull/6).

Это исключительно оптимизационный этап. Ни одна игровая механика не менялась: те же фазы такта в том же
порядке, те же математические операции, те же приоритеты `tier`/`pushChainIndex`, те же правила доставки
и победы, та же нумерация сфер `t_N` и тот же порядок событий. Изменены только структуры поиска внутри
двух проверок и один лишний повторный расчёт канонического порядка.

### 9.1. Что оптимизировано

| Место | Было | Стало |
| --- | --- | --- |
| `collisions.ts`, проверка встречного обмена (`new1 == old2 && new2 == old1`) | двойной цикл по всем парам сфер: `n(n−1)/2` сравнений | локальный индекс `Map<HexKey, string>` «гекс на начало такта → сфера» и **один** проход по каноническому списку сфер |
| `collisions.ts`, канонический порядок сфер | `sortedTokens(world)` вызывался **четыре** раза за такт (дуги ротатора, край/корпус, обмен, наложения) | один `sortedTokens(world)` на такт, результат переиспользуется всеми четырьмя проверками |
| `spawning.ts`, проверка занятости выхода | `Array.from(world.tokens.values()).some(t => hexEqual(t.coord, spawnCoord))` на каждый готовый источник | локальный `Set<HexKey>` строится один раз за фазу и обновляется сразу после каждого выпуска |

### 9.2. Сложность

| Проверка | До | После |
| --- | --- | --- |
| Встречный обмен | `O(n²)` сравнений (при `n = 1000` — 499 500) | построение индекса `O(n)`, поиск `O(n)`; вместе с канонической сортировкой `O(n log n)` |
| Канонический порядок сфер в фазе разрешения | 4 × `O(n log n)` | 1 × `O(n log n)` |
| Занятость выходов источников | `O(S · T)` (`S` источников, `T` сфер) | `O(T + S)`, а если ни один источник не проверяет выход — `O(S)` без построения индекса |
| Память | — | `O(n)` на такт для индекса сфер, `O(T)` на фазу для индекса источников; оба локальны и умирают вместе с вызовом |

Здесь **не** утверждается, что вся фаза разрешения столкновений стала линейной: каноническая сортировка
сфер остаётся `O(n log n)`. Линейной стала именно проверка обменов после получения упорядоченного списка,
и именно это требовалось. Дополнительные сортировки внутри цикла не создавались — наоборот, их стало
меньше (четыре → одна).

### 9.3. Индексные структуры

```ts
// collisions.ts
interface TokenStartIndex {
  tokenAtStart: Map<HexKey, string>;       // гекс начала такта → сфера
  extraAtStart: Map<HexKey, string[]>;     // только для повреждённых состояний (2+ сферы на гексе)
}
buildTokenStartIndex(orderedTokens)                        // O(n), один проход
findHeadOnSwapConflict(world, index, orderedTokens, …)      // O(n), один проход

// spawning.ts (внутри activateSpawners)
let occupiedHexes: Set<HexKey> | null = null;   // создаётся при первой проверке занятости
occupancyIndex().has(spawnKey)                  // O(1); после выпуска — occupancyIndex().add(spawnKey)
```

Индекс стартовой занятости — **локальный**: он создаётся в `resolveMovement` и не попадает в
`SimulationWorld`. Индекс занятости источников — тоже локальный: он живёт только внутри
`activateSpawners`. Глобального состояния и нового `TickContext` нет.

### 9.4. Аргументация эквивалентности

**A. Встречный обмен.**

1. Инвариант B (после каждого завершённого такта на гексе не более одной сферы) означает, что индекс
   `гекс → сфера` биективен: каждая стартовая клетка указывает ровно на одну сферу. Уникальность
   безопасна по той же причине, что и раньше: два входа в сумматор/весы появляются только в
   *предлагаемых* координатах, не в стартовых.
2. Старое условие обмена `new_i = old_j ∧ new_j = old_i` симметрично, то есть задаёт инволюцию: у сферы
   не более одного партнёра. Значит пары обмена **не пересекаются**.
3. Поэтому первый (в лексикографическом порядке `i < j` двойного цикла) конфликт — это первая в
   каноническом порядке сфера, участвующая в обмене, вместе со своим единственным партнёром. Партнёр
   находится по индексу за `O(1)`, а проход по каноническому списку находит ровно ту же пару. Порядок
   координат в подсветке сохранён: `[start первой сферы, start партнёра]`.
4. Исключение `swapper` проверяется тем же предикатом (`intent1.kind === 'swap' && intent2.kind === 'swap'
   && pivot1 == pivot2`), но теперь только для найденной пары-кандидата, а не для каждой пары.
5. Порядок классов проверок не менялся: край → корпус механизма → узкий разлом → встречный обмен →
   наложение. Новый глобальный приоритет не вводился.
6. Повреждённое состояние (несколько сфер на одном стартовом гексе) не «оптимизируется молча»:
   `extraAtStart` хранит дополнительные сферы этого гекса, и кандидаты перебираются в том же
   каноническом порядке, что и в двойном цикле. Поведение на недопустимых данных тоже совпадает.

**B. Занятость выхода источника.**

1. `activateSpawners` вызывается из `processMechanisms` **после** `applyMovement`, поэтому индекс строится
   по координатам после фазы движения: клетка, освобождённая в этом такте, видна источнику сразу.
2. Внутри фазы сферы только добавляются (выпуск) и никогда не удаляются. Поэтому индекс, построенный в
   любой момент фазы, содержит все стартовые координаты; после каждого выпуска координата добавляется
   немедленно — два источника не могут выпустить сферы в одну клетку.
3. Индекс строится **лениво**, при первой же проверке занятости. Это не меняет результат (см. п. 2), но
   сохраняет прежнюю стоимость в тактах, где ни один источник не готов: перезарядка, исчерпанная
   последовательность, уровни без источников.
4. Правило общего выхода из PR #4B сохранено полностью: источники перебираются в каноническом порядке
   координат (`sortedMachines` → меньший `q`, затем меньший `r`), первый занимает гекс, остальные
   получают событие `blocked` и не расходуют ни значение, ни `spawnIndex`, ни `cooldown`.

**C. Проверки «край» и «корпус».**

Они по-прежнему находятся в одном цикле по сферам (`for (const [id, targetCoord] of orderedProposed)`):
для каждой сферы сначала проверяется выход за платформу, затем корпус механизма, и только после этого
цикл переходит к следующей сфере. Это существующее поведение **не менялось** и нового глобального
приоритета между классами не вводилось: при двух независимых нарушениях в одном такте диагностика

### 9.7. Ограничения применимости

1. Эквивалентность доказана для состояний, где выполняется инвариант B (не более одной сферы на гексе).
   Для повреждённых данных индекс хранит дополнительные сферы гекса (`extraAtStart`) и перебирает их в
   каноническом порядке — поведение тоже совпадает, но этот путь не оптимизирован.
2. Индекс обмена строится заново каждый такт: `O(n)` памяти. Кэшировать его между тактами нельзя —
   после `applyMovement` координаты меняются.
3. Проверка обмена остаётся частью фазы с канонической сортировкой `O(n log n)`; «линейной» стала только
   сама проверка.
4. `Set<HexKey>` использует строковые ключи. Для очень маленьких состояний это доминирующая стоимость,
   поэтому индекс строится лениво: уровни без источников и такты перезарядки не платят вовсе.
5. Измерения сняты на одной машине и одном Node; абсолютные миллисекунды не переносимы, отношение
   «старый/новый» при больших `n` устойчиво, при малых — в пределах шума.

### 10.2. Почему без дискретизации

Гекс — пересечение шести полуплоскостей `n_i·x ≤ b_i`, `φ_i = 60°·i`, `b_i = n_i·C_hex + r_h`. Подстановка
точки дуги `x(t) = C + R·(cos(β + σt), sin(β + σt))` даёт `cos(σt + β − φ_i) ≤ (b_i − n_i·C)/R`, то есть
**один угловой интервал на окружности**. Пересечение шести интервалов с диапазоном `t ∈ [0, π/3]` — точный
набор интервалов, где сфера внутри гекса. Пустой набор или проникновение меньше `1e-7` рад — касание либо
отсутствие контакта; всё остальное — пройденный гекс. Кандидаты отбираются по расстоянию от пивота
(`|dist − R| > HEX_SIZE` отбрасывается), поэтому стоимость не зависит от размера платформы.

Порядок результата: по параметру первого входа дуги в гекс, при равенстве — по `q`, затем `r`. Это совпадает
с контрактом и делает диагностику стабильной.

### 10.3. Правило промежуточных траекторий

Занятость гекса дуги считается по объединению **«начало ∪ конец»** такта для всех сфер вне поворачиваемого
компонента:

* сфера, покидающая сектор конвейером/толкателем в этом же такте, всё равно перекрывает дугу в момент
  прохождения поворачивающейся сферы → такт отклоняется целиком;
* сфера, въезжающая в сектор в этом же такте, тоже блокирует поворот;
* сферы самого компонента препятствием не являются (движутся вместе с дугой);
* твёрдый корпус механизма на гексе дуги блокирует поворот всегда.

Поскольку такт либо применяется целиком, либо откатывается, «проскакивания» объектов друг сквозь друга не
возникает: сферы, чьи траектории пересекаются с дугой, просто не двигаются в этом такте.
