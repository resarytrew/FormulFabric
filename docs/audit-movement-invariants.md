`documentDivergence` проверяет, что ожидаемое и фактическое поведение действительно расходятся, и печатает
таблицу аудита в выводе `npm test`. После исправления такой тест упадёт — это и есть сигнал перевести его в
разряд обычных проверок (`assertMatchesRule`). Принудительно потребовать выполнение правил можно командой:

```bash
AUDIT_STRICT=1 npm test   # все задокументированные расхождения становятся падениями
```

## 5. Что зафиксировано по пунктам 3.1–3.4

### 3.1. Столкновения в `collisions.ts`: O(n²) → O(n)

* Текущий двойной цикл по `world.tokens.keys()` действительно даёт n(n−1)/2 сравнений (4950 при 100 сферах,
  499 500 при 1000).
* Готов **эталон эквивалентности**: тест `swap index: linear index and the O(n²) scan agree on 1500 seeded
  configurations with the swapper exception` строит 1500 случайных раскладок, считает вердикт независимой
  линейной реализацией из плана и требует совпадения с текущим перебором.
* Важно: **исключение swapper — не мёртвый код.** 180°-поворот переставляет сферы через две клетки
  (`pivot ± dir`), и такая пара попадает в условие `new1 == old2 && new2 == old1`. Тест
  `the swapper exception covers its own two-hex exchange, while two jumpers exchanging spheres collide`
  фиксирует и это, и обратный случай: обмен двух сфер трамплинами без сваппера — столкновение.
* Предположение об уникальности стартовых гексов безопасно: инвариант B гарантирует, что после каждого
  завершённого такта на гексе не больше одной сферы (проверяется фаззингом), а двойной вход в сумматор/весы
  существует только в *предлагаемых* координатах, не в стартовых.
* Порядок проверок нельзя переставлять: текущий перебор обмена выполняется **после** проверок края, корпуса,
  разлома и **до** проверки наложений. Линейный индекс обязан сохранить этот порядок, иначе изменятся тексты
  ошибок в сценариях с несколькими нарушениями сразу (см. `simultaneous-collision-report`).

### 3.2. Стабильный `compareIntents`

Сейчас выбор действительно зависит от порядка обхода: см. `equal-intent-choice` и
`pusher-magnet-move-source`. Координаты не меняются, поэтому это P2. Тесты готовы к переключению на
`assertMatchesRule` после введения `compareIntents` (сначала tier/signature, затем `pushChainIndex`,
координата источника, тип механизма).

### 3.3. Геометрия вращения

* Математика в порядке: `R^6 = id`, `R^3∘R^3 = id`, `d(R(A),R(B)) = d(A,B)` — проверено исчерпывающе на
  сетке ±6 и на всех парах ±4 для трёх пивотов и шагов ±1/±3.
* 60° свободного вращения полимера, корпус на дуге, «чужая» сфера на дуге, корпус в точке назначения,
  сваппер-поворот полимера на 180°, атомарность при корпусе в точке назначения — всё работает.
* Выборка дуги: для радиусов 2–5 десять точек покрывают **200-точечную эталонную выборку в протестированных координатах**; это не строгое доказательство непрерывного покрытия всей геометрической дуги. На радиусе 6 обнаружен пропуск. Характеризующий тест теперь сравнивает список пропущенных клеток с **пустым списком**, то есть обе стороны выражают одну и ту же величину. Для PR #4D необходима проверка пересечения траектории с гексами без зависимости результата от фиксированной частоты выборки.

### 3.4. Источники и индексы занятости

* Критерий синхронности зафиксирован тестом `sources: occupancy is checked after movement, so a hex freed in
  the same tick can be used immediately`: источник обязан видеть мир **после** фазы движения.
* Ожидание при занятом выходе и последующий выпуск проверены отдельным тестом; два источника на одной линии
  не перезаписывают значения друг друга.
* Индекс занятости нужно строить локально в `activateSpawners` и обновлять сразу после создания сферы
  (как в плане). Общий `TickContext` по-прежнему не нужен: других потребителей индекса нет.
