# Architecture

`src/engine/hex-engine.ts` is the public compatibility entry point and the tick coordinator. A tick resets visual interpolation, builds connected components, computes movement intents, resolves collisions, applies movement simultaneously, runs spawners and arithmetic mechanisms, processes assembly/recycling, then checks deliveries, deadlocks and victory. A failed phase returns immediately. This order is part of the game rules.

Iteration order is part of the game rules, not an artefact of the `Map`: every phase that has an observable effect walks machines, spheres and conflict hexes through `deterministic-order.ts` (coordinates `q` then `r`, machines by coordinate, spheres by `spawnOrder`, then coordinate, then `id`), and equal-priority movement intents are resolved by `intent-order.ts` (`tier` → `pushChainIndex` → source coordinate → machine type). New spheres are therefore numbered `t_N` in a canonical order, the surviving sphere of an adder merge is the oldest one, and error messages/highlights are stable when several collisions happen in one tick. `world.visitedHexes` is a `Set` metric: its contents are order independent, its insertion order is not part of the contract.

The individual phases live in `movement-intents.ts`, `collisions.ts`, `movement-apply.ts`, `spawning.ts`, `mechanisms.ts`, `assembly.ts`, `delivery.ts` and `victory.ts`. `operations.ts` holds exact integer operations; `patterns.ts`, `components.ts` and `rotation.ts` implement matching and geometry. `placement-validation.ts` owns one definitive machine arrangement (`resolveFinalPlacement`) and reports structured `PlacementIssue`s (code, message, exact cells, block index), so the editor highlights only contested cells: locked fixtures, presets the player replaced, and the player blocks that survive geometry and collision rules. `validateLevelPlacement` and `createWorldFromLevel` both consume it, so a validated layout and the built world cannot disagree, and multi-hex receiver pads are checked cell by cell. Pattern linting lives in `pattern-lint.ts` (integer values within the engine token range, in-range and deliverability-checked expectations, connectivity of multi-node patterns, hex-adjacency of every edge — the welder bonds only neighbours — per-mode rules for `sum_shape` / `beam_balance` / `growth_ladder`; open chains stay legal), and `machine-config.ts` rejects invalid machine parameters before a layout is accepted or a world is built — out-of-range divisors, malformed filter rules, rotator modes, over-long spawner sequences and, as an explicit game rule, coincident main and side exits on two-output devices (`dup`, `halver`, `divmod`, `scales`, `filter`; `splitter` alternates outputs and is exempt). Both modules read corrupted configs defensively. Delivery goals are accounted per sink in `verification.ts` (`getRequiredBySink` treats expected values and polymers of one delivery as one requirement, never their sum; combined scalar+polymer expectations are rejected for multi-sphere sinks and must agree per delivery for single-node sinks; expected sink ids must exist and be unique) and enforced by `hasCompletedGoals` in `victory.ts`, so a large total cannot compensate for a starved receiver. The primary stream derives the same per-sink quotas from the embedded sequences of the level's receiver patterns (where they uniquely determine the delivery count), and `verifyLevelSolution` always reports the primary stream as its own row alongside every additional stream, checking expectation compatibility before running any of them. `layout-conflicts.ts` reports why a stored variant would not build instead of silently deleting its blocks (and lists records the scene cannot draw at all, so they can be removed deliberately), delegating to the same `validateLevelPlacement` used before a simulation starts; `createEditableWorldFromLevel` keeps an invalid layout on the board as an error world so conflicts stay visible and fixable (replacing a preset is only allowed from its centre hex, never from one of its pads); `verifyLevelSolution` validates before running the primary and additional verification streams. World state is mutable during a tick; `cloneWorld` makes the independent snapshots used by the UI and rewind.

`chapters/` contains the four puzzle chapters. `machine-catalog.ts` owns the tool list and labels, while `levels.ts` retains the existing public exports and sandbox definition. `coordinates.ts`, `game-types.ts`, `level-types.ts`, `visual-types.ts` and `models/ui.ts` separate model definitions; `types.ts` remains a compatibility barrel.

`App.tsx` composes editor, edit-history, progress, simulation-step and simulation-clock hooks. `services/storage.ts` isolates persisted data. The scene receives simulation events explicitly; `useSceneEvents.ts` schedules their effects, `eventEffects.ts` maps them to visual cues, `animateMachines.ts` updates mechanism animation, `sceneInput.ts` owns pointer and keyboard input, `useSceneCamera.ts` handles camera commands, and `disposeObjectTree.ts` owns object-tree disposal. Mesh signatures include conveyor topology and theme, so unchanged models can be retained.

`npm test` runs engine, renderer and storage tests. Fixtures record complete world state at every tick for all 29 demo solutions, 42 verification streams, and selected arithmetic and collision failures, using the pre-refactor engine as reference. These fixtures do not substitute for visual playback, browser interactions, or exhaustive testing of arbitrary user-created layouts.

Validation protects the public construction and solution-verification paths against invalid placements and limits. The game runs entirely on the client and exposes mutable world objects; this is not a security boundary against a caller that deliberately mutates state or replaces code. Authoritative anti-cheat would require a trusted verifier outside the client.
