# Architecture

`src/engine/hex-engine.ts` is the public compatibility entry point and the tick coordinator. A tick resets visual interpolation, builds connected components, computes movement intents, resolves collisions, applies movement simultaneously, runs spawners and arithmetic mechanisms, processes assembly/recycling, then checks deliveries, deadlocks and victory. A failed phase returns immediately. This order is part of the game rules.

The individual phases live in `movement-intents.ts`, `collisions.ts`, `movement-apply.ts`, `spawning.ts`, `mechanisms.ts`, `assembly.ts`, `delivery.ts` and `victory.ts`. `operations.ts` holds exact integer operations; `patterns.ts`, `components.ts` and `rotation.ts` implement matching and geometry. `placement-validation.ts` owns one definitive machine arrangement (`resolveFinalPlacement`): locked fixtures, presets the player replaced, and the player blocks that survive geometry and collision rules. `validateLevelPlacement` and `createWorldFromLevel` both consume it, so a validated layout and the built world cannot disagree, and multi-hex receiver pads are checked cell by cell. The same module lints receiver target patterns (duplicate vertices, out-of-range or duplicate edges, per-delivery row lengths) and reads corrupted configs defensively. `layout-conflicts.ts` reports why a stored variant would not build instead of silently deleting its blocks, delegating to the same `validateLevelPlacement` used before a simulation starts; `createEditableWorldFromLevel` keeps an invalid layout on the board as an error world so conflicts stay visible and fixable (replacing a preset is only allowed from its centre hex, never from one of its pads); `verifyLevelSolution` validates before running the primary and additional verification streams. World state is mutable during a tick; `cloneWorld` makes the independent snapshots used by the UI and rewind.

`chapters/` contains the four puzzle chapters. `machine-catalog.ts` owns the tool list and labels, while `levels.ts` retains the existing public exports and sandbox definition. `coordinates.ts`, `game-types.ts`, `level-types.ts`, `visual-types.ts` and `models/ui.ts` separate model definitions; `types.ts` remains a compatibility barrel.

`App.tsx` composes editor, edit-history, progress, simulation-step and simulation-clock hooks. `services/storage.ts` isolates persisted data. The scene receives simulation events explicitly; `useSceneEvents.ts` schedules their effects, `eventEffects.ts` maps them to visual cues, `animateMachines.ts` updates mechanism animation, `sceneInput.ts` owns pointer and keyboard input, `useSceneCamera.ts` handles camera commands, and `disposeObjectTree.ts` owns object-tree disposal. Mesh signatures include conveyor topology and theme, so unchanged models can be retained.

`npm test` runs engine, renderer and storage tests. Fixtures record complete world state at every tick for all 29 demo solutions, 42 verification streams, and selected arithmetic and collision failures, using the pre-refactor engine as reference. These fixtures do not substitute for visual playback, browser interactions, or exhaustive testing of arbitrary user-created layouts.

Validation protects the public construction and solution-verification paths against invalid placements and limits. The game runs entirely on the client and exposes mutable world objects; this is not a security boundary against a caller that deliberately mutates state or replaces code. Authoritative anti-cheat would require a trusted verifier outside the client.
